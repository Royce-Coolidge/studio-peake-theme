# Coding Conventions

**Analysis Date:** 2026-03-16

## Naming Patterns

**Files:**
- Liquid components: kebab-case (e.g., `sp-focal-image.liquid`, `newsletter-popup.js`)
- Sections: kebab-case (e.g., `announcement-bar.liquid`, `footer-group.json`)
- Snippets: kebab-case (e.g., `css-variables.liquid`, `sp-gradient-overlay.liquid`)
- Blocks: kebab-case (e.g., `button.liquid`, `image.liquid`)
- JavaScript assets: kebab-case (e.g., `studio-peake.js`, `newsletter-popup.js`)
- CSS files: kebab-case (e.g., `studio-peake.css`, `custom-fonts.css`)

**Functions (JavaScript):**
- camelCase for function names (e.g., `copyDiscountCode()`, `fallbackCopyText()`, `showCopySuccess()`)
- Verb-first convention for action functions (e.g., `showCopySuccess`, `copyDiscountCode`)
- Private functions follow same camelCase convention

**Variables (JavaScript):**
- camelCase for all variables (e.g., `codeElement`, `copyBtn`, `copiedText`, `codeText`)
- DOM element references often include descriptive suffixes (e.g., `copyBtn`, `copiedText`)
- Template literal usage with camelCase identifiers

**Variables (Liquid):**
- snake_case_with_hyphens for Liquid variable assignments (e.g., `sp_sizes`, `sp_widths`, `sp_focal`)
- Prefix with component name for scoped variables (e.g., `sp_*` for Studio Peake components)
- All lowercase with hyphens separating words

**CSS Classes:**
- kebab-case for CSS class names
- BEM-like convention with double underscore for elements: `.component__element`
- Modifier suffix with double hyphen: `.component--modifier`
- Studio Peake custom classes prefixed with `.sp-` (e.g., `.sp-link-group`, `.sp-focal-image`, `.sp-is-visible`, `.sp-gradient-overlay`, `.sp-adaptive--portrait`)
- Status/state classes prefixed with `.is-` or `.sp-is-` (e.g., `.sp-is-visible`)

**CSS Custom Properties (Variables):**
- kebab-case with double hyphen prefix (e.g., `--container-max-width`, `--section-vertical-spacing`, `--text-h1`)
- Grouped by category in root selectors (e.g., Container, Typography, Spacing, Colors)
- Color values stored as RGB without `rgb()` wrapper: `var(--text-color)` used with `rgb(var(--text-color))`

**IDs and Data Attributes:**
- kebab-case (e.g., `discount-code-text`, `data-action="close"`)
- Section IDs auto-generated by Shopify: `shopify-section-{{ section.id }}`

## Code Style

**Formatting:**
- No explicit linter configuration detected in codebase
- HTML/Liquid: 2-space indentation
- CSS: 2-space indentation
- JavaScript: 2-space indentation
- Liquid tag formatting: balanced, readable structure with proper spacing

**Linting:**
- Not detected - no .eslintrc, eslint.config.js, or biome.json found
- Code follows consistent JavaScript conventions by pattern

**Liquid Code Organization:**
- Comment headers use dashed separator lines: `----------------------------------------------------------------------------------------------------------------------`
- Top comment block documents component purpose and supported variables
- Variable documentation uses markdown-like format within Liquid comments

## Import Organization

**JavaScript:**
- ES module imports at top of file (e.g., `import { inView } from "vendor"`)
- Vendor imports prefixed with "vendor" alias (via importmap)
- Single import statement per file followed by code blocks

**Liquid Snippets:**
- Render statements use full parameter passing: `{% render 'snippet-name', param1: value1, param2: value2 %}`
- Parameters passed with explicit key:value syntax
- Comments above render calls document parameter purpose

**CSS Organization:**
- Custom properties defined at top in `:root` selector
- Grouped by category with comment section headers
- Component-specific styles below root variables
- Media queries at bottom of rule sets

## Error Handling

**JavaScript Patterns:**
- Guard clauses at function entry: `if (!codeElement || !copyBtn) return;`
- Early return pattern for missing elements
- Try/catch blocks for operation fallbacks (e.g., clipboard API with fallback)
- Console logging for errors: `console.error('Failed to copy text: ', err);`
- No custom error types or error classes detected

**Liquid Patterns:**
- Blank/empty checks: `if image == blank` or `if text != blank`
- Conditional assignment: `{%- assign sp_sizes = sizes | default: '100vw' -%}`
- Nil/empty filters in assignments: `| default: 'value'`
- Negative conditions avoided (use positive assertions)

**Fallback Patterns:**
- Modern API with fallback approach (e.g., clipboard API with execCommand fallback)
- Feature detection before usage: `if (navigator.clipboard && window.isSecureContext)`

## Logging

**Framework:** Native `console` object

**Patterns:**
- Error logging: `console.error('Failed to copy text: ', err);`
- Minimal logging - only for errors, not debug/info
- Error messages descriptive but concise

## Comments

**When to Comment:**
- Component purpose headers at top of Liquid snippets
- Feature/interaction explanations (e.g., `// === SP Link Keyline Draw-On (INTR-04, Phase 4) ===`)
- Algorithm implementation notes (e.g., note about focal point fallback)
- Complex CSS selectors explained inline

**Comment Styles:**
- Liquid: `{%- comment -%} ... {%- endcomment -%}` for block comments
- Liquid: `{% comment %}...{% endcomment %}` for documentation blocks
- JavaScript: `//` for single line, `/* */` for blocks
- CSS: `/* */` for all comments
- Section separators use repeated dashes: `/* === Feature Name (REF-XX) === */`

**JSDoc/TSDoc:**
- Not used - native JavaScript without TypeScript
- Parameter documentation done in Liquid comments above snippets

## Function Design

**Size:** Functions are small and focused
- `copyDiscountCode()`: 15 lines (main logic)
- `fallbackCopyText()`: 15 lines (error handling path)
- `showCopySuccess()`: 7 lines (state update)

**Parameters:**
- Named parameters in Liquid: explicit key-value pairs
- JavaScript uses multiple DOM element references when needed
- Default values provided via Liquid filters: `| default: '100vw'`

**Return Values:**
- Early returns for guard conditions
- No explicit returns in state-change functions
- Event handlers don't return values
- Functions either return nothing (void) or operate on DOM directly

## Module Design

**Exports:**
- ES module pattern: `import { inView } from "vendor"`
- No explicit module exports - direct DOM manipulation via querySelector

**Barrel Files:**
- No barrel files detected
- Snippets included via `{% render %}` with parameter passing
- Sections group multiple snippets via JSON configuration files

**Component Structure:**
- One component per file (e.g., `button.liquid`, `banner.liquid`)
- Liquid snippets accept parameters via `render` tag
- JSON configuration files group sections (e.g., `header-group.json`, `footer-group.json`)
